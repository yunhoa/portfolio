# 작업지시서 - 경력기술서 포맷

## 2026.10 최신 경력기술서 기준

이 섹션이 최신 기준이다. 아래의 기존 템플릿 설명보다 우선한다.

경력기술서는 프로젝트를 빠르게 훑는 문서다. React 포트폴리오와 PDF 포트폴리오에서 대표 사례를 깊게 풀기 때문에, 경력기술서에서 모든 프로젝트마다 문제/판단/결과를 길게 반복하지 않는다.

프로젝트별 기본 구조:

```text
프로젝트명
참여기간 YYYY.MM ~ YYYY.MM

개요
프로젝트가 무엇인지 1~2문장

역할
내가 실제로 맡은 개발 업무

기술
실제 사용 기술
```

프로젝트명 아래에는 참여기간만 쓴다. `참여기간 2026.01 ~ 2026.07 · FastAPI · RAG`처럼 기술을 섞지 않는다.

### 주요 수행 업무

상단 주요 수행 업무는 대표 업무만 적는다.

- Java / Spring 기반 서버 기능 개발 및 운영 시스템 유지보수
- MyBatis, SQL, Oracle/PostgreSQL 기반 데이터 조회·처리 기능 개발
- REST API 및 외부 시스템 연동 기능 개발
- Morpheus 기반 모바일 웹뷰와 Spring 백엔드 연계 개발
- FastAPI 기반 검색·데이터 처리 API 개발

JMeter, GA API, DMZ Proxy는 상단 주요 업무가 아니라 해당 프로젝트 본문에 넣는다.

### 프로젝트 순서

Java/Spring 서버 지원 기준:

1. 한화오션 안전혁신과제
2. 3D 산단 디지털 플랫폼 유지관리
3. MySafety 작업자 안전 지원 모바일 플랫폼
4. 광역단위 노후 건축물 디지털 안전워치 플랫폼 스마트 검색 서비스
5. 스마트플랜트 설비 이미지 전처리 및 메타정보 생성
6. 메디컬트윈 기반 병원 운영관리 통합 플랫폼
7. 반도체 제조공정 IoT·디지털트윈 융합 모니터링 플랫폼

### 최신 프로젝트 역할 문구 예시

한화오션 역할:

> 모바일 화면 이벤트, 백엔드 API, MyBatis Mapper, Oracle SQL 흐름을 따라가며 구조를 파악했고, 4개 모바일 모듈의 화면 기능과 Spring 백엔드 데이터 처리 로직을 구현했습니다. MyBatis Mapper와 Oracle SQL을 작성해 공지·문의·자료·MSDS 조회·마일리지 신청 등 주요 업무 기능을 개발했으며, 모듈 간 화면 작성 규칙도 정리했습니다. 동영상 업로드·재생 기능에서는 Range 요청에 따른 Spring Controller 응답 범위 처리와 JMeter 부하테스트 시나리오를 직접 구성했습니다.

3D 산단 역할:

> Spring Boot 기반 서버 기능 개발, JPA 기반 기능 개발, PostgreSQL 운영 데이터 조회, SQL 작성, Thymeleaf 화면 개발을 진행했습니다. 관리자 통계 기능에 Google Analytics Data API를 연동했고, 폐쇄망 운영 환경에서 외부 API 호출이 실패하는 문제는 DMZ Apache Proxy를 통한 연동 경로를 적용해 처리했습니다.

MySafety 역할:

> Apache Cordova 기반 모바일 앱 개발 및 유지보수를 담당했습니다. Background Geolocation을 활용한 위치 수집 기능을 구현했고, WebView에서 처리하기 어려운 위치 기능은 네이티브 영역과 연동해 처리했습니다. Android/iOS 스토어 배포 과정에서 인증서와 배포 설정을 구성하고, 스토어 정책에 맞춰 로그인 및 앱 실행 흐름을 수정했습니다. Firebase 연동, 실제 단말 테스트, Android OS 업데이트에 따른 앱 실행 이슈 대응도 진행했습니다.

## AI 에이전트 지시사항 (Codex / Claude 등에게)

너는 이 문서를 받아 사용자의 경력기술서를 완성해주는 도우미다.

1. 먼저 사용자가 `01-포트폴리오-사이트-작업지시서.md`를 이미 진행했는지 물어라. 이미 진행해서 프로젝트별 문제/판단·해결/역할/결과 답변이 있다면, 그 내용을 그대로 가져다 아래 구조로 재배치만 해라 (처음부터 다시 묻지 않는다). 안 했다면 아래 순서대로 새로 물어라.
1-1. 사용자에게 "프로젝트가 몇 개인지"부터 물어라. 그다음 프로젝트 하나씩 아래 "입력받을 정보"를 순서대로 질문해라. 한 프로젝트를 다 채운 뒤 다음 프로젝트로 넘어가라. 각 질문에 붙어 있는 "예시"를 같이 보여줘서 참고하게 해라 (그대로 베끼라는 게 아님을 밝힌다).
2. 질문 순서는 "무슨 프로젝트였는지 → 맡은 역할 → 어떤 문제가 있었는지 → 어떻게 판단했는지 → 결과" 순서를 지켜라. 사용자가 짧게 답해도 되니 처음부터 완성된 문장을 요구하지 마라.
3. 사용자가 짧게/키워드로만 답하면, 하단 "문장 틀"을 이용해 문장으로 다듬어 보여주고 확인을 받아라.
4. "검토만 했다"와 "실제로 구현/적용했다"를 반드시 구분해서 물어보고, PoC 수준이면 그렇게 명시해라.
5. 모든 프로젝트 정보를 받으면 하단 "예시 스켈레톤"의 `{{TOKEN}}`을 답변으로 치환해서 프로젝트별 경력기술서 텍스트 초안을 만들고, 이어서 하단 "PDF 출력용 HTML 템플릿"도 같은 값으로 채워서 `경력기술서_{{NAME}}.html` 파일로 저장해라. 텍스트만 주고 끝내지 마라 — 이 HTML을 브라우저로 열면 `PDF로 저장` 버튼으로 바로 PDF를 뽑을 수 있어야 한다.
6. 지원 직무를 알고 있다면(문서 `04`에서 이미 물어봤다면) 그 직무와 관련 있는 프로젝트를 앞쪽에 배치해라.
7. 사용자에게 초안을 보여주기 전에 "작성 원칙"과 "제출 전 점검 체크리스트"로 먼저 스스로 검토해라. 특히 한 줄 요약이 사소한 트러블슈팅 하나로 축소되지 않았는지, 원인 분석이 "고쳤습니다"로 뭉뚱그려지지 않았는지 확인하고 **걸리는 부분은 스스로 고친 뒤에 제시**해라. 무엇을 왜 고쳤는지 한 줄로 같이 알려줘라.

### 입력받을 정보 (프로젝트마다 반복, 각 항목 예시 포함)

1. 프로젝트명 / 소속(회사·기관) / 기간 / (선택) 팀 규모·기여도 — 예: `사내 안전관리 시스템 고도화 / OO소프트 / 2025.03 – 진행 중 / 4인 팀`
2. 한 줄 요약 — 예: `Spring Framework 기반 레거시 백엔드와 Morpheus 하이브리드 웹뷰를 함께 맡아 교육이력관리 시스템 기능을 개발했다.` (사소한 이슈 하나가 아니라 업무 범위 전체가 드러나야 함 — 아래 "작성 원칙"의 나쁜 예/좋은 예 참고)
3. (선택) 배경: 왜 이 작업을 하게 됐는지 — 예: `기존 시스템의 동영상 재생 기능에 대한 개선 요구가 있어 착수했다.`
4. 문제: 어떤 문제/요구사항이 있었는지 (구체적 상황) — 예: `모바일 웹뷰와 Spring 레거시 백엔드를 함께 개발해야 했고, 동영상 업로드·재생 기능은 실제 시청 흐름까지 확인할 필요가 있었다.`
5. 판단·해결: 어떻게 접근했고 왜 그 방법을 선택했는지 (다른 대안을 검토했다면 그것도) — 예: `Morpheus 기반 모바일 화면과 Spring Framework 백엔드 기능을 함께 개발하고, Range 요청에 따라 Spring Controller의 영상 응답 범위를 처리했다.`
6. 맡은 역할 / 구현한 기능 (여러 개 가능) — 예: `Range 처리 API 개발`, `JMeter 부하테스트 시나리오 구성`
7. 결과: 수치나 확인 가능한 근거 (없으면 "수치 없음"이라고 답해도 됨 — 지어내지 말 것) — 예: `동시 사용자 50명·100명·150명 조건에서 응답시간, 오류 여부, Throughput을 확인했다.`
8. 사용 기술 (면접에서 설명 가능한 것만) — 예: `Java, Spring Framework, MyBatis, SQL, Morpheus, JavaScript, JMeter`

## 목적

프로젝트 단위로 "무슨 문제가 있었고, 어떻게 판단해서, 어떤 결과를 냈는지"를 구조화해서 보여준다. 이력서보다 상세하고, 자기소개서의 문제 해결 경험 문단은 여기서 재료를 가져온다.

## 구조 (프로젝트 1개당 아래 항목을 반복)

1. **프로젝트명 / 소속(회사·기관) / 기간 / (선택) 팀 규모·기여도**
2. **한 줄 요약**
3. **배경**: 왜 이 작업을 하게 됐는지 (회사 프로젝트에서 자명하면 생략 가능)
4. **문제**: 어떤 문제 또는 요구사항이 있었는지, 구체적인 상황으로 서술
5. **판단·해결**: 어떻게 접근했고 왜 그 방법을 선택했는지
6. **내가 맡은 역할 / 구현한 기능**: 불릿 리스트
7. **결과**: 수치나 확인 가능한 근거 위주로, 과장하지 않고 사실 그대로
8. **사용 기술**: 면접에서 설명할 수 있는 것만

가장 중요한 세 항목은 **문제 / 판단 / 결과**다. 이 세 개가 프로젝트 설명의 핵심이 되고, 자기소개서 문제 해결 경험 문단의 재료가 된다.

## 문장 틀 예시 (`{{TOKEN}}`을 답변으로 치환)

- 문제: `{{ENVIRONMENT}} 환경에서 {{PROBLEM}} 문제가 있었습니다.`
- 판단: `{{REASON}} 이유로 {{APPROACH}} 방식을 선택했습니다.` / `{{ALTERNATIVE}} 방식도 검토했지만, {{CONSTRAINT}} 제약 때문에 {{APPROACH}}을 택했습니다.`
- 결과: `{{ACTION}}을 통해 {{RESULT}} 결과를 확인했습니다.`
- PoC 수준 표현: `{{SCOPE}}까지 PoC 수준으로 검토했습니다.` (실제 운영 적용과 구분해서 쓸 것)

## 작성 원칙

- 없는 경력이나 수치를 만들지 않는다.
- "검토했습니다", "이해했습니다"보다 실제로 했다면 "구현했습니다", "개발했습니다", "수행했습니다"로 쓴다.
- PoC 수준과 실제 적용/운영을 명확히 구분해서 쓴다.
- 프로젝트가 여러 개면 지원 직무와 맞는 경험을 앞쪽에 배치한다.
- 면접에서 설명하지 못할 기술명은 사용 기술에 넣지 않는다.
- **작은 트러블슈팅 하나를 "한 줄 요약"/프로젝트 대표 설명으로 삼지 않는다.** 프로젝트 기간 내내 한 이슈만 판 게 아니라면, 한 줄 요약은 실제로 맡았던 업무 범위 전체(어떤 기능을 개발/운영했는지)를 기준으로 쓰고, 그 트러블슈팅 사례는 "맡은 역할"이나 "결과" 항목 하나로 내려서 넣는다.
  - 나쁜 예 (요약): `OO 인식 오류를 수정했다` — 몇 달짜리 프로젝트의 대표 설명이 사소한 버그 수정 하나로 축소됨
  - 좋은 예 (요약): `{{도메인}} 서비스의 백엔드 기능 개발 및 운영 유지보수를 담당했다` — 전체 업무 범위가 드러나고, 버그 수정 사례는 결과 항목에 별도로 기재
- **원인 분석은 확인한 범위를 순서대로 보여준다.** "고쳤습니다"로 끝내지 말고, 실제로 어느 레이어까지 좁혀가며 확인했는지 나열한다 (예: 화면 → 요청/응답 → 서버 로직 → SQL/DB → 외부 API → 네트워크). 실제로 확인하지 않은 범위까지 지어내지 않는다.
- **주요 수행 업무는 대표 업무만 적는다.** 예를 들어 `폐쇄망 운영 환경의 외부 API 연동 문제 대응`, `JMeter 기반 동영상 기능 부하테스트`처럼 특정 프로젝트 안의 부수 경험은 상단 주요 업무가 아니라 해당 프로젝트의 성과/결과에 넣는다.
- **프로젝트 본문은 `담당 / 성과 / 기술` 양식을 기본으로 한다.** 예: 담당에는 개발한 기능 범위를 쓰고, 성과에는 구현 결과와 확인한 지표를 쓴다.

## PDF 출력용 HTML 템플릿

텍스트만으로 끝내지 말고, 아래 HTML도 `{{TOKEN}}`을 채워서 `경력기술서_{{NAME}}.html` 파일로 저장해라. 브라우저로 열면 우측 상단 `PDF로 저장` 버튼(`window.print()`)으로 바로 PDF를 뽑을 수 있다.

CSS 클래스명(`.doc`, `.doc-header`, `.two-col`, `.project`, `.project-body` 등)과 `@media print`/`@page` 규칙은 `02`번 문서와 동일하게 `통합-지원문서-생성기.html`의 경력기술서 출력 화면에서 그대로 가져온 것이다. `02`의 HTML을 이미 만들었다면 `<style>` 블록은 거의 그대로 재사용하면 된다 (이 문서에서만 쓰는 `.two-col`, `.project`, `.project-body`만 추가). 구조/CSS는 손대지 말고 `{{TOKEN}}`만 채워라.

```html
<!doctype html>
<html lang="ko">
<head>
<meta charset="UTF-8" />
<meta name="viewport" content="width=device-width, initial-scale=1.0" />
<title>{{NAME}} 경력기술서</title>
<style>
  :root {
    --bg: #eef2f6;
    --paper: #ffffff;
    --ink: #172033;
    --muted: #64748b;
    --line: #d7dee8;
    --soft: #f6f8fb;
    --accent: #2563eb;
  }
  * { box-sizing: border-box; }
  html { color-scheme: light; }
  body {
    margin: 0;
```

## 제출 전 점검 체크리스트

- [ ] 프로젝트마다 역할 / 문제 / 판단 / 결과가 모두 들어갔는지
- [ ] 수치나 확인 가능한 근거가 있는지
- [ ] 남아있는 `{{TOKEN}}`이 없는지 (텍스트 버전과 HTML 버전 둘 다)
- [ ] 면접에서 설명 못 할 기술명이 없는지
- [ ] 지원 직무와 관련 있는 프로젝트가 앞쪽에 배치됐는지
- [ ] HTML을 브라우저로 열어 `PDF로 저장` 버튼을 눌렀을 때 프로젝트 카드가 페이지 중간에서 어색하게 잘리지 않는지
