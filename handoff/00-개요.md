# 작업지시서 모음 - 개요

이 폴더는 "다른 사람이 나처럼 React 포트폴리오 사이트를 만들고, 같은 포맷으로 이력서/경력기술서/자기소개서를 쓰고 싶을 때" 그대로 넘겨줄 수 있는 작업지시서 묶음입니다.

각 문서(`.md`)는 사람이 읽고 따라 해도 되고, **Codex나 Claude 같은 코딩 에이전트에게 파일 하나를 그대로 붙여넣어도** 동작하도록 만들어졌습니다. 각 문서 맨 위 "AI 에이전트 지시사항" 섹션이 있어서, 에이전트가 이 문서를 받으면 스스로 "필요한 정보를 순서대로 질문 → 답변으로 템플릿 채우기" 흐름으로 동작합니다. 즉 md 파일만 넘겨줘도 상대방에게 "이름 입력해주세요", "이메일 입력해주세요" 같은 질문이 자동으로 나오게 되어 있습니다.

## 문서 목록

| 문서 | 내용 | 결과물 |
| --- | --- | --- |
| `01-포트폴리오-사이트-작업지시서.md` | React + Vite + Tailwind 포트폴리오 사이트 전체 코드 템플릿 (컴포넌트/CSS 구조를 원본 그대로 포함) | 실행 가능한 React 프로젝트 |
| `02-이력서-포맷-작업지시서.md` | 이력서 구조 + 문장 틀 | 이력서 텍스트 + PDF 출력용 HTML |
| `03-경력기술서-포맷-작업지시서.md` | 프로젝트별 역할/문제/판단/결과 구조화 방식 | 경력기술서 텍스트 + PDF 출력용 HTML |
| `04-자기소개서-포맷-작업지시서.md` | 지원동기~입사 후 방향 서술 구조 | 자기소개서 텍스트 + PDF 출력용 HTML |
| `05-심플-통합문서-작업지시서.md` | 이력서+경력기술서+자기소개서를 종이 한 장처럼 이어붙인 문서 (React 사이트가 부담스러운 사람용 대안) | 통합 문서 1개 (텍스트 + PDF 출력용 HTML) |

`02`~`05`는 텍스트만 뱉고 끝내지 않는다. 각 문서 끝의 "PDF 출력용 HTML 템플릿"까지 채워서 `.html` 파일로 저장해야 결과물이 완성된 것이다. 이 HTML은 원래 쓰던 `통합-지원문서-생성기.html`(브라우저에서 입력하면 이력서/경력기술서/자기소개서를 만들고 `PDF로 저장` 버튼으로 바로 인쇄하던 도구)의 실제 CSS/마크업을 그대로 가져온 것이다 — `01`번 문서가 React 컴포넌트 원본을 그대로 박아 넣는 것과 같은 방식이다. `02`/`03`/`04`는 카드형(그림자, 알약 배지) 디자인을 쓰고, `05`는 같은 원본에서 가져오되 그림자·배지 없이 종이 문서처럼 더 담백한 디자인을 쓴다 — 그 차이가 두 방식의 존재 이유다. `02`/`03`/`04`끼리는 `<style>` 블록이 거의 동일하니(`02`를 만들었으면 `03`/`04`는 거기에 몇 개 클래스만 더하면 된다) 한 사람이 셋 다 만들 때는 `02`의 `<style>`을 먼저 완성하고 재사용해라.

### `01`(React 사이트) vs `05`(심플 통합 문서), 뭘 쓸까

- 프로젝트가 많고 화면으로 넘기며 보여주고 싶다, 웹 개발 역량 자체도 어필하고 싶다 → `01`
- 지원 서류는 그냥 심사자가 인쇄하거나 PDF로 훑어볼 문서 하나면 된다, 웹사이트까지는 부담스럽다 → `05`
- 정답은 없다. 둘 다 만들어서 사이트는 포트폴리오 링크로, `05`는 지원 시스템에 첨부하는 PDF로 같이 쓰는 사람도 있다. 이 경우에도 내용(회사명/기간/기술/문제/결과)은 반드시 동일해야 한다 — 아래 "문서 간 일관성 점검"을 `05`에도 적용해라.

## 진행 순서: `01`이 원본 데이터, `02`~`05`는 거기서 파생

이 다섯 문서는 따로따로 완성하는 게 아니라 **`01`에서 받은 답변(이름/학력/경력/기술/프로젝트별 문제·판단·결과)이 원본이고, `02`(이력서)·`03`(경력기술서)·`04`(자기소개서)·`05`(심플 통합 문서)는 그 원본을 포맷에 맞게 재가공한 결과물**이다. 같은 프로젝트를 놓고 사이트에는 A라고 써있고 이력서에는 B라고 써있으면 안 된다. `05`는 `01` 없이 혼자 써도 되지만, `01`을 이미 했다면 마찬가지로 그 답변을 재사용한다.

1. **`01`번을 가장 먼저 진행한다.** 여기서 받는 질문(기본 정보, 학력/경력, 기술 스택, 프로젝트별 문제/판단·해결/역할/결과)이 가장 자세하고, 나머지 문서가 필요로 하는 정보를 전부 포함한다. `01`(React 사이트)이 필요 없고 `05`(심플 통합 문서)만 필요해도, 질문 자체는 `01`의 순서를 따라도 된다.
2. **`02`~`05`번을 진행할 때는 새로 묻기 전에 `01`번 답변이 이미 있는지 먼저 확인한다.** 있으면 그 값을 그대로 재사용하고, 포맷에 맞게 다시 묻지 않는다 (예: 프로젝트의 "문제/판단·해결/결과"는 `01`에서 받은 그대로 `03`/`05`의 문제/판단·해결/결과 항목에 넣고, `04`/`05`의 "문제 해결 경험" 문단은 그 내용을 풀어쓴 것이어야 한다). `01`을 아직 안 했다면 그 문서에 있는 순서대로 새로 물어봐도 된다.
3. 결과적으로 **하나의 원본 콘텐츠가 사이트/이력서/경력기술서/자기소개서/통합 문서 다섯 가지 형태로만 다르게 나온다.** 사실관계(회사명, 기간, 기술, 수치, 문제/결과)는 전체 문서에서 동일해야 하고, 문장의 길이·톤만 포맷에 맞게 달라진다 (사이트/이력서는 압축, 경력기술서는 구조화, 자기소개서는 서술형, 통합 문서는 그 셋을 한 장에 이어붙인 형태).
4. 사진, PDF, 스크린샷 같은 이미지 자료는 완전히 선택이다. 실제로 보여줄 파일이 있을 때만 진행하고, 없으면 해당 카드/섹션을 통째로 만들지 않는다. 원본 포트폴리오에 있던 특정 이미지를 그대로 가져다 쓰지 않는다 — 어디까지나 지금 작업하는 사람 본인의 자료로 채운다.

### 코딩 에이전트(Codex, Claude Code 등)에게 넘길 때
1. `01-포트폴리오-사이트-작업지시서.md` 내용을 그대로 프롬프트로 붙여넣는다. 에이전트가 "AI 에이전트 지시사항"을 따라 이름/이메일/학력/경력/기술/프로젝트를 섹션별로 물어보고, 답변을 받으면 실제 파일(`package.json`, `src/components/*.jsx`, `src/data/*.js` 등)을 생성한다. 사이트 자체가 필요 없다면 `01`을 건너뛰고 `05`부터 시작해도 된다.
2. `02`~`05` 문서를 이어서 붙여넣을 때, 같은 대화(같은 에이전트 세션)라면 앞서 받은 답변을 그대로 재사용하라고 한 줄 알려준다 (예: "위에서 답한 프로젝트 내용 그대로 써줘"). 새 대화/새 세션이면 `01`에서 만든 `data/projects.js`, `data/skills.js`, `Hero.jsx`의 내용을 함께 붙여넣어서 에이전트가 다시 질문하지 않고 재사용하게 한다.
3. 컴포넌트 구조와 CSS(className)는 문서 안에 원본 그대로 박혀 있으므로, 에이전트가 임의로 레이아웃을 바꾸지 않는 한 원본과 동일한 화면이 나온다.

### 사람이 직접 따라 할 때
1. `01`번 문서의 코드 템플릿을 그대로 파일로 옮기고 `{{TOKEN}}` 부분만 본인 내용으로 교체한다.
2. `02`~`05`번 문서의 "예시 스켈레톤"/HTML 템플릿에서 `{{TOKEN}}`을 채울 때, `01`에서 이미 쓴 프로젝트별 문제/판단/결과를 그대로 가져다 포맷만 바꾼다. 처음부터 다시 생각해내지 않는다.
3. 필요한 문서를 다 완성하면 아래 "문서 간 일관성 점검"으로 마무리한다.

## 문서 간 일관성 점검 (필요한 문서를 다 끝낸 뒤 한 번씩)

- [ ] 회사명·기간·재직 기간(년/개월) 계산이 `01`(사이트)·`02`(이력서)·`03`(경력기술서)·`05`(통합 문서)에서 전부 같은지
- [ ] 같은 프로젝트의 핵심 기술 스택이 문서마다 다르게 적혀 있지 않은지 (예: 한쪽엔 A/B/C, 다른 쪽엔 A/D만 적혀 있으면 안 됨)
- [ ] 같은 프로젝트의 "결과"로 적은 수치나 근거가 문서마다 다르지 않은지
- [ ] `04`/`05`(자기소개서)의 "문제 해결 경험" 문단이 `03`(경력기술서)의 어떤 프로젝트에서 나온 내용인지 바로 알 수 있는지 (근거 없이 새로 지어낸 문단이 아닌지)
- [ ] 이력서(`02`)처럼 압축된 문서와 자기소개서(`04`)처럼 풀어쓴 문서를 나란히 읽었을 때 같은 사람의 같은 경험처럼 읽히는지
- [ ] `01`과 `05`를 둘 다 만들었다면, 같은 프로젝트가 두 문서에서 서로 다른 회사명/기간/결과로 적히지 않았는지

## 공통 원칙 (모든 문서에 동일하게 적용)

- 하지 않은 경험이나 없는 수치는 만들지 않는다.
- PoC(검토 수준)와 실제 적용/구현을 구분해서 쓴다.
- 지원 직무와 관련 없는 세부 내용은 줄인다.
- 자기소개서도 과장된 홍보 문구보다 경력기술서처럼 담백하게 쓴다.
- 면접에서 설명하지 못할 기술명은 넣지 않는다.
- 문서 전체에서 빈칸 표시는 `{{TOKEN}}` 형식으로 통일했다. 최종 결과물에 `{{...}}`가 남아있으면 작업이 끝난 게 아니다.

## 최신 기준 예시 - Java/Spring 백엔드 지원용

2026.10 기준으로 조윤호 포트폴리오와 지원문서는 아래 방향을 최신 기준으로 둔다. 새 문서를 만들 때는 이 기준을 먼저 확인한다.

- 경력 표기: `올포랜드 IE팀 / 사원 · 2025.01 ~ 재직 중 (1년 9개월) · Java/Spring 기반 서버 기능 개발 및 운영 시스템 유지보수`
- 학력 표기: `경민대학교 컴퓨터소프트웨어과(3년제) · 재학기간 2019.03 ~ 2025.02 · 학점 3.94 / 4.5`
- 주요 수행 업무는 대표 업무만 적는다. 예: `Java / Spring 기반 서버 기능 개발 및 운영 시스템 유지보수`, `MyBatis, SQL, PostgreSQL 기반 데이터 조회·처리 기능 개발`, `REST API 및 외부 시스템 연동 기능 개발`, `Morpheus 기반 모바일 웹뷰와 Spring 백엔드 연계 개발`
- JMeter, DMZ Proxy, Google Analytics Data API 같은 부수 경험은 상단 주요 업무에 과하게 올리지 말고, 해당 프로젝트 본문에서 설명한다.
- 한화오션 프로젝트는 `교육이력관리 시스템`, `Spring Framework`, `MyBatis`, `Morpheus`, `동영상 업로드·재생`, `Range 응답`, `JMeter`를 중심으로 쓴다.
- 3D 산단 프로젝트의 Google Analytics Data API는 프로젝트 전체 대표 업무가 아니라 `관리자 통계 기능의 일부`로 표현한다.
- 자기소개서는 공고 내용을 길게 설명하지 말고, `기존 서비스와 데이터 흐름을 빠르게 파악하고 필요한 백엔드 기능을 실제 구현까지 연결하는 사람`이 보이게 쓴다.

## 품질 기준: 실제로 고쳤던 사례 (일반화)

아래는 실제 포트폴리오 작업 중 "처음 쓴 버전이 왜 별로였는지, 어떻게 고쳤는지"를 일반화한 것이다. `02`~`05`를 채울 때, 그리고 최종 점검할 때 같은 실수를 하지 않았는지 비교해라.

1. **작은 트러블슈팅 하나를 프로젝트 전체의 대표 설명으로 삼지 마라.**
   - 나쁜 예: 몇 달짜리 프로젝트인데 대표 설명이 "OO 인식이 안 되는 버그를 고쳤다"는 한 가지 이슈로 요약됨. 실제로는 그 프로젝트에서 기능 개발/운영 유지보수를 폭넓게 했는데, 정작 사소한 이슈 하나만 부각되어 프로젝트 전체 기여가 작아 보임.
   - 좋은 예: 프로젝트의 핵심 업무 범위(어떤 기능을 개발했고 어떤 역할을 맡았는지)를 먼저 대표 설명으로 쓰고, 그 트러블슈팅은 "맡은 역할" 또는 "결과" 항목 하나로 내린다. 지원 직무와 가장 관련 있는 업무를 앞세운다.
2. **경력/프로젝트 한 줄 요약은 기술 키워드 나열이 아니라 "무슨 일을 했는지" 문장으로 쓴다.**
   - 나쁜 예: `백엔드/API, 프레임워크 A/B 연동 및 플랫폼 유지보수` (기술 이름만 나열)
   - 좋은 예: `SI 프로젝트 풀스택 개발 및 운영 시스템 유지보수` (무슨 일을 했는지 한 문장으로)
   - 세부 기술 스택은 상단 요약에서 다 풀지 말고, 프로젝트 카드/경력기술서 본문에서 풀어라.
3. **원인 분석을 설명할 때는 한 레이어에서 멈추지 말고 확인한 범위를 그대로 보여준다.**
   - 나쁜 예: "버그를 찾아서 고쳤다"로 끝남.
   - 좋은 예: "화면 → 요청/응답 → 서버 로직 → SQL/DB → 외부 API → 네트워크 구간까지 나눠서 원인을 확인했다"처럼, 실제로 어디까지 좁혀갔는지 순서대로 보여준다. (안 해본 범위까지 지어내면 안 됨 — 실제로 확인한 범위만 쓴다.)
4. **프로젝트 분류를 정확히 해라.** 실제로는 회사 업무로 진행한 프로젝트인데 "기타/시각자료" 같은 애매한 분류에 넣으면 기여도가 작아 보인다. 회사 프로젝트면 회사 프로젝트로 분류하고, 배포 규모·사용자 수 같은 실제 수치가 있으면 반영해라.
5. **개인 프로젝트에는 회사 프로젝트용 "문제/판단·해결" 틀을 억지로 씌우지 마라.** 개인 프로젝트는 "왜 만들었는지(배경)"와 "무엇을 구현했는지(기능)"가 더 자연스럽다. 트러블슈팅 사례가 있으면 결과나 구현 내용 항목에 자연스럽게 녹여라.
