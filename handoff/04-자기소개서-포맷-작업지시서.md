# 작업지시서 - 자기소개서 포맷

## AI 에이전트 지시사항 (Codex / Claude 등에게)

너는 이 문서를 받아 사용자의 자기소개서를 완성해주는 도우미다.

1. 먼저 지원 회사명과 지원 직무를 물어라. (이 두 값은 문서 `03`의 경력기술서에서 어떤 프로젝트를 앞세울지 정하는 데도 쓰인다.)
2. 사용자가 이미 문서 `01`(사이트) 또는 `03`(경력기술서)을 작성했다면 그 내용을 재료로 그대로 써라 — 새로 묻지 말고, 거기 적힌 프로젝트의 문제/판단/결과를 문단으로 풀어쓰기만 해라. 둘 다 없다면 "문제 해결 경험" 항목을 채우기 전에 간단히 프로젝트 하나를 먼저 물어봐라 (문서 `03`의 질문 순서를 참고해라).
3. 아래 "입력받을 정보"를 섹션 단위로 순서대로 질문해라. 각 질문에 붙어 있는 "예시"를 같이 보여줘서 참고하게 해라 (그대로 베끼라는 게 아님을 밝힌다).
4. 회사 공고에 문항별 글자수 제한이 있는지 물어보고, 있다면 먼저 길게 쓴 뒤 분량에 맞춰 줄이는 순서로 작업해라.
5. 모든 답변을 받으면 하단 "예시 스켈레톤"의 `{{TOKEN}}`을 답변으로 치환해서 완성된 자기소개서 텍스트를 출력하고, 이어서 하단 "PDF 출력용 HTML 템플릿"도 같은 값으로 채워서 `자기소개서_{{NAME}}_{{TARGET_COMPANY}}.html` 파일로 저장해라. 텍스트만 주고 끝내지 마라 — 이 HTML을 브라우저로 열면 `PDF로 저장` 버튼으로 바로 PDF를 뽑을 수 있어야 한다.
6. 완성 후 "작성 원칙"을 기준으로 스스로 점검해라. 특히 없는 경험을 지어내지 않았는지, 공고 키워드를 억지로 반복하지 않았는지 확인해라.
7. 사용자에게 보여주기 전에, 채용담당자 입장에서 한 번 더 소리 내어 읽듯이 검토해라: (a) 어느 문장이 과장/홍보 문구처럼 들리는지, (b) 각 문장이 실제 경험(경력기술서 내용)에 근거하는지, (c) 그 문장 그대로 면접에서 "이 부분 더 설명해주세요"라는 질문을 받으면 답할 수 있는지. 걸리는 문장이 있으면 스스로 고친 뒤에 제시하고, 무엇을 왜 고쳤는지 한 줄로 알려줘라.

### 입력받을 정보 (섹션별로 순서대로 질문, 각 항목 예시 포함)

**1) 지원 정보**
- 지원 회사명, 지원 직무, (선택) 문항별 글자수 제한

**2) 지원동기**
- 왜 이 회사/직무에 관심을 갖게 됐는지 (계기) — 예: `여러 프로젝트를 경험하면서 화면 자체보다 그 뒤에서 요청과 데이터가 어떻게 처리되는지 확인하는 일에 더 흥미를 느꼈습니다.`
- 지원 이유 — 예: `기존 서비스와 데이터 흐름을 빠르게 파악하고 필요한 백엔드 기능을 실제 구현까지 연결하는 경험을 이어갈 수 있다고 생각해 지원합니다.`

**3) 직무역량**
- 핵심 기술/경험 2~3개 요약 (경력기술서 내용 압축) — 예: `Java/Spring 기반 서버 기능 개발`, `MyBatis와 SQL 기반 데이터 처리`, `REST API 및 외부 시스템 연동`

**4) 문제 해결 경험**
- (경력기술서에서 정리한) 상황 → 문제 → 판단/행동 → 결과 — 예: `한화오션 프로젝트에서 처음 접한 Morpheus와 Spring Framework 기반 레거시 환경을 파악해 모바일 기능부터 백엔드, MyBatis 연동과 SQL 작성까지 개발했습니다. 동영상 업로드·재생 기능에서는 Range 요청에 따라 Spring Controller의 영상 응답 범위를 처리하고, JMeter로 동시 사용자 50명·100명·150명 조건에서 응답시간과 오류 여부를 확인했습니다.`
- 새로 지어내지 말고 반드시 `03`(경력기술서)에 이미 적힌 프로젝트에서 그대로 가져올 것

**5) 강점 / 일하는 방식**
- 강점 1~2가지 + 각각을 뒷받침하는 구체적 사례 — 예: `문제가 생기면 화면부터 서버, DB, 네트워크까지 구간을 나눠서 원인을 좁혀가는 방식으로 일합니다. OO 프로젝트에서 외부 API 호출 실패의 원인을 네트워크 구간(DMZ Proxy)까지 확인해 해결한 사례가 있습니다.`

**6) 입사 후 방향**
- 지원 회사에서 하고 싶은 것 (현실적인 범위로) — 예: `입사 후에는 지금까지 해온 Java/Spring 기반 API 개발, MyBatis와 SQL 데이터 처리, 외부 시스템 연동 경험을 바탕으로 서비스 기능 개발과 운영 과정의 데이터·연동 문제를 함께 다루고 싶습니다.` (막연한 포부보다 지금까지의 경험에서 자연스럽게 이어지는 방향으로)

---

## 목적

지원동기부터 입사 후 방향까지 이어지는 서술형 문서를 작성한다. 내용의 재료는 경력기술서(`03`번 문서)에서 정리한 실제 프로젝트 경험이며, 여기서 새로 지어내지 않는다.

## 구조

1. **지원동기**: 왜 이 회사/직무인지. 공고 키워드를 억지로 반복하지 않는다.
2. **직무역량**: 핵심 기술/경험 요약. 경력기술서의 압축본.
3. **문제 해결 경험**: 경력기술서의 문제/판단/결과를 문단으로 풀어서 서술 (상황 → 문제 → 행동 → 결과 순서)
4. **강점 / 일하는 방식**: 1~2가지, 반드시 구체적 사례와 함께
5. **입사 후 방향**: 지원 회사에서 하고 싶은 것. 막연한 포부보다 현실적인 방향

## 문장 틀 예시 (`{{TOKEN}}`을 답변으로 치환)

- 지원동기: `{{EXPERIENCE}} 경험을 통해 {{INTEREST}}에 관심을 갖게 되었고, {{REASON}} 부분에서 먼저 기여할 수 있다고 생각해 {{COMPANY}}에 지원합니다.`
- 직무역량: `저는 {{CORE_STACK}} 기반으로 {{DOMAIN}}을 개발/운영해온 개발자입니다.`
- 문제 해결 경험: `{{SITUATION}} 상황에서 {{PROBLEM}} 문제가 있었고, {{REASON}} 이유로 {{APPROACH}} 방식을 선택해 {{RESULT}} 결과를 확인했습니다.`
- 강점: `저는 {{SITUATION_TYPE}}할 때 {{WORKING_STYLE}}하는 방식으로 일합니다. {{PROJECT}} 프로젝트에서 {{EXAMPLE}} 사례가 있었습니다.`
- 입사 후 방향: `입사 후에는 {{STRENGTH}}을 바탕으로 {{CONTRIBUTION}}에 기여하고 싶습니다.`

## 작성 원칙

- 경력기술서보다 문장이 부드러워도 되지만, 없는 사실을 지어내지 않는다.
- 공고 키워드를 억지로 반복하지 않는다. (검색 노출이 아니라 실제 읽는 사람을 위한 글임을 기억할 것)
- 각 문단은 경력기술서의 실제 프로젝트 경험에서 재료를 가져온다.
- 문항별 글자수 제한이 있는 채용 공고라면, 먼저 위 구조대로 길게 쓰고 나서 줄이는 순서로 작업한다.

## 예시 스켈레톤

```text
[지원동기]
{{TRIGGER_EXPERIENCE}} → {{INTEREST}} → {{APPLICATION_REASON}}

[직무역량]
{{CORE_SKILL_SUMMARY}}

[문제 해결 경험]
{{SITUATION}} → {{PROBLEM}} → {{JUDGMENT}} → {{RESULT}}
(경력기술서 03번 문서의 문제/판단/결과를 그대로 가져와서 문단으로 풀기)

[강점 / 일하는 방식]
{{STRENGTH_STATEMENT}} + {{CONCRETE_EXAMPLE}}

[입사 후 방향]
{{POST_HIRE_DIRECTION}}
```

## PDF 출력용 HTML 템플릿

텍스트만으로 끝내지 말고, 아래 HTML도 `{{TOKEN}}`을 채워서 `자기소개서_{{NAME}}_{{TARGET_COMPANY}}.html` 파일로 저장해라. 브라우저로 열면 우측 상단 `PDF로 저장` 버튼(`window.print()`)으로 바로 PDF를 뽑을 수 있다.

`<style>` 블록은 `02`/`03`번 문서와 같은 `통합-지원문서-생성기.html` 원본에서 가져온다. 자기소개서는 카드형 대신 서술형이라 `.doc-coverLetter`(폭을 좁히고 문단을 양쪽 정렬하는 클래스)만 추가로 쓴다. `02`/`03`의 `<style>`을 이미 만들었다면 `.doc-coverLetter` 규칙만 더하면 된다. 구조/CSS는 손대지 말고 `{{TOKEN}}`만 채워라.

## 체크리스트

- [ ] 지원 회사명/직무명이 정확히 들어갔는지 (다른 회사 지원서 복붙 흔적 없는지)
- [ ] 각 문단이 실제 경험(경력기술서 내용)에 근거하는지
- [ ] 남아있는 `{{TOKEN}}`이 없는지 (텍스트 버전과 HTML 버전 둘 다)
- [ ] 공고에서 요구한 문항별 글자수 제한을 지켰는지
- [ ] 소리 내어 읽었을 때 자연스러운지 (과장된 홍보 문구처럼 들리지 않는지)
- [ ] HTML을 브라우저로 열어 `PDF로 저장` 버튼을 눌렀을 때 문단이 양쪽 정렬로 깔끔하게 나오는지
